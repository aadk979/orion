## Known gaps

These are real, current, and documented rather than hidden.

<Accordion allowMultiple>
  <AccordionItem title="The committed SDK bundle predates DPoP">
    `Packages/client/dist/orion.beta.sdk.js` contains no `createProof` and no
    `DPoP` header — the source in `lib/` does. Additionally, the `Orion`
    constructor calls `new ApiInterface(serverUrl, nameSpace, slug)` with no
    options argument, so `options.useDpop` is never set. Enabling
    `tokens.binding: 'dpop'` therefore requires rebuilding the SDK **and** wiring
    that flag through. See [Building the SDK](/versions/alpine/docs/sdk/building-the-sdk).
  </AccordionItem>
  <AccordionItem title="Abuse detection is per-node">
    Counters live in process memory rather than Redis, so thresholds are
    effectively per-node on a cluster. The `abuse-high` consensus topic exists
    partly to compensate — it lets you ask whether an attack is fleet-wide.
  </AccordionItem>
  <AccordionItem title="The tier-1 jti denylist degrades without Redis">
    It falls back to an in-process map, which is correct for a single node and
    per-node on a cluster. Run Redis if you use tier 1.
  </AccordionItem>
  <AccordionItem title="Inert configuration keys">
    `utilities.dataIntegrity.dip` appears in the shipped config template but is
    no longer read — the DIP subsystem was decommissioned. It is harmless, but it
    is not doing anything.
  </AccordionItem>
  <AccordionItem title="Documentation referencing a missing entry point">
    `Packages/apps/Todos-App/README.md` still instructs you to run
    `orchestrator/start.js`, which is not in the repository. Build one from
    `Packages/server/Orion-Orchestrator/examples/orchestrator.example.js`.
    The root `DEPLOYMENT.md` has been corrected.
  </AccordionItem>
  <AccordionItem title="No built-in health endpoint">
    There is no `/health` route. Declare your own custom endpoint, or point your
    load balancer at a cheap real one.
  </AccordionItem>
  <AccordionItem title="No down migrations">
    Schema rollback is not supported. Because migrations are additive, reverting
    code and leaving the schema is the practical path; a genuinely bad migration
    means restoring from backup.
  </AccordionItem>
</Accordion>

## Where the project is headed

<Callout type="info" title="Direction, not commitment">
The items below reflect the shape of the work in the repository — open
extension points, partially-generalised systems, and gaps the code itself flags.
None of them are dated promises.
</Callout>

- **Finish the DPoP rollout path.** Rebuild and republish the SDK bundle with
  proof generation wired through, so token binding is a config change rather
  than a source change.
- **Distributed abuse state.** Moving abuse counters onto the shared ephemeral
  store would make thresholds fleet-wide rather than per-node.
- **Configuration surface cleanup.** Removing the inert `dataIntegrity.dip` key
  from the shipped `orion.config.example.js`. `DEPLOYMENT.md` now documents it as
  inert rather than live.
- **Broader secrets-manager domains.** The registry already supports arbitrary
  `kind` / `domain` pairs; today only `access`, `refresh`, `resource`, and
  `internal` are created at boot.
- **More reference applications.** The Todos app proved its worth by surfacing
  four real bugs the unit suite never exercised.

## Reading the real changelog

The most reliable record of what changed and why is
`lib/Utils/Databases/migrations/`. Each file opens with a comment block naming
the issue it addresses and the reasoning behind the fix. Read those before an
upgrade.
