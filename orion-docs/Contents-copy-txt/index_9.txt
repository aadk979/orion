By the end of this section you will have one `Orion-core` node running against a
Postgres database, and a browser page that signs a user up, signs them in, and
holds the session across a reload.

That is the whole first milestone. Clustering, the orchestrator, the admin
plane, and TLS all come later — none of them are needed to get auth working.

<Steps>
  <Step title="Prerequisites">
    Node.js 18.18+ (20 LTS recommended) and a Postgres database. SMTP
    credentials if you want
    passkeys, TOTP, device authorization, or password reset — Orion-core
    force-disables those methods when `mail` is absent.
    [Read the full list →](/versions/alpine/docs/getting-started/prerequisites)
  </Step>
  <Step title="Run your first node">
    Copy the annotated config template, fill in your Postgres credentials, and
    call `initiateServer()`. Schema migration runs automatically on boot.
    [Walkthrough →](/versions/alpine/docs/getting-started/first-node)
  </Step>
  <Step title="Your first sign-in">
    Point the browser SDK at the node, call `signUpUser` and `signInUser`, and
    subscribe to `onAuthStateChanged`.
    [Walkthrough →](/versions/alpine/docs/getting-started/first-sign-in)
  </Step>
</Steps>

Once that milestone is done, [Next steps](/versions/alpine/docs/getting-started/next-steps) lays
out the order most deployments take from there.

<Callout type="tip" title="There is a working app in the repo">
`Packages/apps/Todos-App` is a complete integration — Express API on Orion-core
with custom `/todos` routes, a static HTML/JS client using the SDK, and an
orchestrator process. If you would rather read working code than a tutorial,
start there. See [Examples](/versions/alpine/docs/examples).
</Callout>

## What it does not do

- It is **not** a hosted identity provider. There is no Orion cloud to sign up for.
- It is **not** an OAuth *provider*. Orion consumes OAuth from Google, GitHub and
  friends; it does not issue OAuth tokens to third parties.
- It does **not** ship a UI. The SDK gives you the calls; the screens are yours.
- Sessions are **not** replicated node-to-node by R_Sync. Session state lives in
  Postgres; signing keys are shared through Redis. R_Sync carries control-plane
  traffic only.
