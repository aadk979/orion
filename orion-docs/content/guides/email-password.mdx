The simplest method, and the only one that works with no SMTP credentials
configured.

## Enable it

```js filename="gipsy.orion.config.js"
authMethods: {
    emailPassword: true,
    allowedEmailDomains: ['*']      // or ['example.com', 'corp.io']
}
```

`allowedEmailDomains` is either the single wildcard `['*']` or a list of real
domains. Mixing them fails the boot:

```text
Configuration conflict: Cannot mix wildcard '*' with specific domains.
Use either ['*'] or specific domains like ['company.com']
```

An omitted or empty array defaults to allow-all with a warning.

## Sign up

```js
const result = await orion.signUpUser(email, password);

if (result.error) {
    // e.g. ACCOUNT-REGISTRATION::EMAIL-IN-USE, DATA-VALIDATION::INVALID-DATA::A::p
    showError(result.errorCode);
}
```

Server-side validation on `sign-up-user` requires a valid email and a password of
at least 7 characters. Password strength is additionally scored with zxcvbn, and
the hash is bcrypt.

Email uniqueness is **case-insensitive** — enforced by a functional unique index
on `lower(email)`, so `Ada@example.com` and `ada@example.com` are the same
account.

### Reacting to account creation

`utilities.onUserCreation` is called with the new user. Use it to provision
application-side records:

```js filename="gipsy.orion.config.js"
utilities: {
    onUserCreation: async user => {
        await db.query('INSERT INTO profiles (uid) VALUES ($1)', [user.uid]);
    }
}
```

## Sign in

```js
const result = await orion.signInUser(email, password);
```

<Callout type="info" title="One failure code, several causes">
"No such account", "this account has no password" (an OAuth-only account), and
"wrong password" all return
`ACCOUNT-SIGNIN::INVALID-CREDENTIALS::A::p`. That is deliberate — returning them
separately lets anyone enumerate registered addresses and identify which accounts
have no password to fall back on. Your audit trail still records which one
occurred.
</Callout>

## Failed sign-ins are throttled, not locked

Three columns on the `users` row implement per-account exponential backoff:
`failed_login_count`, `failed_login_window_start`, and `login_throttled_until`.

The important property is what happens when a **correct** credential arrives
during backoff. Orion does not refuse it — that would let anyone who knows an
email address deny its owner service. Instead it returns
`ACCOUNT-SIGNIN::STEP-UP-REQUIRED::A::p` with
`orion-flow-activation: FLOW-STEP-UP-AUTH`, and the user re-verifies by email
OTP, passkey, or TOTP. A successful sign-in clears the backoff.

On top of that, the rate limiter charges cost **5** to `sign-in-user` and
`sign-up-user` — the highest non-extreme tier — and abuse detection blocks an IP
for 15 minutes after 10 authentication failures in a 60-second window.

## Disabled accounts

An administratively disabled account is refused with
`ACCOUNT-SIGNIN::ACCOUNT-DISABLED::A::p`, and its live sessions are torn down on
the next refresh because the middleware re-reads `disabled` from the database
rather than trusting the token. See
[User administration](/versions/alpine/docs/guides/user-administration).

## Turning it off

Set `authMethods.emailPassword: false` and sign-in returns
`ACCOUNT-SIGNIN::EMAIL-PASSWORD-DISABLED::A::p`. Make sure another method is
enabled first, or nobody can get in.
