description: Envelope encryption for encryptable fields, the nine supported vault providers, rotation, and recovery when a key is lost.

Some columns are encrypted before they reach Postgres, so a database dump alone
cannot compromise them. Today that is TOTP two-factor secrets
(`user_totp.secret` and `pending_secret`). The mechanism is generic — new fields
are declared in `Utils/Core/KeyVault/EncryptedFieldRegistry.js` and inherit
rotation, status reporting and recovery for free.

## Envelope encryption

Orion never asks a vault to encrypt each secret directly. It uses a two-level
scheme:

```
  key vault (KEK)          orion_encryption_keys           user_totp
  ───────────────          ─────────────────────           ─────────
  never leaves      wraps  v3  wrapped_key  ACTIVE  seals  enc.v2.3.<iv>.<tag>.<ct>
  the vault         ────►  v2  wrapped_key  retired ────►
                           v1  wrapped_key  retired
```

- The **DEK** (data encryption key) is generated by Orion, stored **wrapped**,
  and used with AES-256-GCM to seal individual values.
- The **KEK** (key encryption key) lives in your vault and only ever wraps and
  unwraps the DEK.

The DEK exists so that reading a TOTP secret on the login path is a local AES
operation rather than a network round trip. Without it, a vault rate limit or a
brief vault outage would become an authentication outage. KEK rotation stays
cheap — re-wrap one small blob — and remains fully effective, because a DEK is
useless without the key that wraps it.

Retired DEK versions are **kept**, so a rotation never strands data.

### Envelope format

| Prefix | Meaning |
| --- | --- |
| *(none)* | Pre-encryption plaintext. Read as-is, re-sealed on next write |
| `enc.v1.` | Legacy inline-key format, AES-256-GCM under `sha256(dataEncryption.key)` |
| `enc.v2.<n>.` | Vault-backed, AES-256-GCM under DEK version `n` |

The DEK version is bound as additional authenticated data, so an envelope cannot
be re-pointed at a different key version by editing the database.

## Choosing a provider

```js filename="gipsy.orion.config.js"
utilities: {
    dataEncryption: {
        provider: 'AWS_KMS',
        region: 'eu-west-1',
        keyId: 'arn:aws:kms:eu-west-1:111122223333:key/1234abcd-…'
    }
}
```

| `provider` | Service | Required keys | Gate |
| --- | --- | --- | --- |
| `INLINE_KEY` | Key in `orion.config.js` | `key` (≥32 chars) | single instance only |
| `AWS_KMS` | AWS Key Management Service | `region`, `keyId` | — |
| `GCP_KMS` | Google Cloud KMS | `projectId`, `location`, `keyRing`, `keyName` | — |
| `AZURE_KEY_VAULT` | Azure Key Vault / Managed HSM | `vaultUrl`, `keyName` | — |
| `HASHICORP_VAULT` | Vault CE or HCP Vault Dedicated (transit) | `address`, `keyName`, `token` \| `roleId`+`secretId` | — |
| `HCP_VAULT` | Alias of the above; add `namespace: 'admin'` | as above | — |
| `OPENBAO` | OpenBao (transit) | `address`, `keyName`, `token` \| `roleId`+`secretId` | — |
| `HCP_VAULT_SECRETS` | HCP Vault Secrets (secret store) | `organizationId`, `projectId`, `appName`, `secretName`, `clientId`, `clientSecret` | `explicitAllow` |
| `AKEYLESS` | Akeyless Vault | `keyName`, `accessId`, `accessKey` | `explicitAllow` |
| `INFISICAL` | Infisical KMS (cloud or self-hosted) | `keyId`, `clientId`, `clientSecret`, `baseUrl` | `explicitAllow` |

Vaultwarden is **not supported**. It implements the Bitwarden password-manager
API, which has no server-side secrets or transit endpoint — retrieving an item
requires client-side crypto derived from a user's master password. There is no
correct way to use it as a KEK.

### Two gates

<Callout type="warning" title="Providers are disabled until you allow them">
Providers marked `explicitAllow` above are **disabled internally**. Naming one in
`provider` is not enough — its config block must also carry
`explicitAllow: true`. Without it the provider is skipped with a loud warning and
encryption is treated as unavailable.

This is the same gate the OAuth toolkit applies to its untested providers, for
the same reason: the integration ships, but it has not been exercised against a
live account in this release, and a key vault is not a thing to discover that
about at 3am.
</Callout>

The second gate is deployment shape. `INLINE_KEY` is **refused in cluster mode**.
A symmetric key copied into every node's config file has no revocation story, no
rotation, and no audit trail, and it multiplies across hosts, images and backups.
One box may hold its own key; a fleet may not.

### Remote-crypto vs. material providers

Two physical shapes sit behind one interface:

- **Remote-crypto** (`AWS_KMS`, `GCP_KMS`, `AZURE_KEY_VAULT`,
  `HASHICORP_VAULT`, `OPENBAO`, `AKEYLESS`, `INFISICAL`) — the wrap and unwrap
  happen *inside* the vault. The KEK never enters Orion's process.
- **Material** (`HCP_VAULT_SECRETS`) — the vault is a secret store with no crypto
  engine, so it returns key material that Orion wraps with locally.

Material providers are weaker and Orion says so at boot: the KEK does reach
process memory. It never reaches disk or config, it is centrally revocable, and
it is auditable at the vault — materially better than a config string — but
prefer a remote-crypto provider where you have one.

Both shapes expose identical methods and identical return shapes. Nothing outside
the provider knows which kind it is talking to.

### Configuration is validated at boot

`utilities.dataEncryption` is checked structurally before anything connects, and
a structural problem **stops the boot**. The distinction is deliberate:

| Class | Examples | Behaviour |
| --- | --- | --- |
| **Structural** — your mistake, deterministic, never self-heals | misspelled key, unknown provider, missing required value, `INLINE_KEY` in cluster, gated provider without `explicitAllow`, wrong type | **throws at boot** |
| **Runtime** — the environment's, may resolve on its own | vault unreachable, credentials rejected, round trip fails | **degrades** — TOTP deactivates, users fall back to emailed codes |

A node that starts anyway would silently run without the protection its own
config claims to configure, which is the worse outcome. Unknown keys are rejected
rather than ignored, with a suggested correction:

```text
Configuration error in utilities.dataEncryption:
  - utilities.dataEncryption.keyid is not a recognized key for AWS Key Management Service — did you mean "keyId"?
  - utilities.dataEncryption.keyId is required by AWS Key Management Service (or set AWS_REGION in the environment).
```

Every error is reported at once, so a misconfigured block is fixed in one pass
rather than one restart per mistake.

<Callout type="info" title="An absent block is not an error">
Omitting `dataEncryption` entirely is tolerated: it deactivates encryptable
fields with a loud log rather than failing, so a first run and any existing
deployment with no TOTP users still starts. Set `required: true` to make its
absence fatal too — recommended for production.
</Callout>

### Credentials

AWS, GCP and Azure use the vendor SDK when it is installed
(`@aws-sdk/client-kms`, `@google-cloud/kms`, `@azure/keyvault-keys`) and fall
back to a built-in signed-REST client otherwise. **No dependency is required.**

Either path resolves credentials the same way: explicit config values →
environment variables → workload identity (IMDSv2, ECS task role, GCE metadata
server, Azure managed identity).

<Callout type="info" title="The boot check is a real round trip">
Initialization wraps a throwaway key and unwraps it again, then compares. A vault
that authenticates and answers `GET /key` perfectly can still be unable to
decrypt — a revoked grant, a raised `min_decryption_version`, a wrong key
version. That is exactly the failure that must not reach production traffic, so
a metadata read is not enough.
</Callout>

## When the vault is unavailable

The node **still boots and still serves**. A vault outage must not escalate into
a total authentication outage.

| | Behaviour |
| --- | --- |
| New enrollments | Refused. Secrets are **never** written in plaintext |
| Enrolled users | Not locked out — TOTP is dropped from their offered methods and they use the **emailed one-time code** |
| Stored secrets | Left untouched; everything resumes when the vault returns |
| Removal | Still allowed, so nobody is trapped with a dead factor |
| The user | Gets an in-product notice via [Orion Notifications](/versions/alpine/docs/guides/notifications) |

Two factors are preserved throughout: the fallback is a real second factor, not a
bypass.

<Warning title="The fallback needs SMTP">
Without `mail` credentials the emailed-code path is also unavailable, and
TOTP-dependent accounts genuinely cannot complete a second factor. The boot log
states this explicitly when it applies.
</Warning>

## Migrating from the inline key

Rows sealed by earlier releases carry the `enc.v1.` prefix. Keep the old key in
config as `legacyKey` so they stay readable, then rotate to re-seal them under
the vault:

```js filename="gipsy.orion.config.js"
dataEncryption: {
    provider: 'AWS_KMS',
    region: 'eu-west-1',
    keyId: 'arn:…',
    legacyKey: 'THE_OLD_INLINE_KEY'   // drop once rotation reports 0 stale rows
}
```

```bash
orionctl keyvault rotate-dek     # new DEK + re-encrypt every sealed row
orionctl keyvault status         # staleRows should read 0
```

Migration is non-breaking: legacy rows keep working throughout, and there is no
downtime window.

## Rotation

```bash
orionctl keyvault status         # provider, health, key ledger, sealed-row counts per node
orionctl keyvault rotate-kek     # rotate the vault key, re-wrap the DEK — data untouched, fast
orionctl keyvault rotate-dek     # new DEK + re-encrypt every sealed row
```

`rotate-kek` is routine hygiene and safe to schedule: only the wrapper changes,
so no user data is touched and no restart is needed. Providers that cannot rotate
through their API (`INFISICAL`, `HCP_VAULT_SECRETS`, `INLINE_KEY`) report that
plainly instead of pretending to succeed — the DEK is still re-wrapped.

`rotate-dek` rewrites every encrypted row in bounded batches. Retired DEKs are
kept, so a partial run strands nothing and re-running is safe. Rows that cannot
be decrypted are **left exactly as they are** rather than overwritten — that
evidence is what a recovery decision depends on.

Both are issued to a single node: the key ledger is shared database state, so
broadcasting would have every node racing on the same rows.

## Recovery when a key is lost

If the KEK is genuinely gone, the only path forward is to discard the unreadable
data and have users re-enroll.

```bash
orionctl keyvault check   # does the fleet agree the data is unrecoverable?
orionctl keyvault wipe --reason "KMS key deleted in incident 2026-07-27"
```

<Warning title="This is irreversible">
Every affected user loses their authenticator enrollment and must set it up
again. Four independent gates must all pass:

1. the caller is **root** — a role check, not a policy grant;
2. the `keyvault:ops:wipe-encrypted` PBAC action is allowed;
3. the phrase `WIPE ENCRYPTED FIELDS` is typed interactively, and is
   **re-checked by the executing node** so no single component can destroy data
   on its own;
4. the fleet votes **unanimously** that encryption is unrecoverable.
</Warning>

Gate 4 is the one that matters most in practice. "The key is gone" is a belief
until the cluster confirms it. If even one node can still decrypt, the data is
not lost and the right action is to repair the others — so the wipe is refused. A
partitioned fleet yields *unknown*, which also refuses. `--override-consensus`
forces past the finding and is recorded in the audit trail alongside the required
reason.

```bash
# extend the reset to the orchestrator's own system admins
orionctl keyvault wipe --reason "…" --admins [--include-root]
```

Root is spared unless `--include-root` is passed: root has no magic-link
fallback, so wiping its authenticator can strand the control plane entirely.

Every affected end user is notified in-product.

## PBAC actions

| Action | Grants |
| --- | --- |
| `keyvault:read:status` | Vault status, health, key ledger, sealed-row counts, and the consensus preview |
| `keyvault:ops:rotate-kek` | Rotate the vault key and re-wrap the DEK |
| `keyvault:ops:rotate-dek` | New DEK and full re-encryption pass |
| `keyvault:ops:wipe-encrypted` | The destructive wipe — **root role is required in addition** |

They live in their own namespace, so a broad `cluster:*` grant never confers the
destructive one.
